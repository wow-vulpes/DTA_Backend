# DTA — проверка комплектности материалов

Java backend для проверки дневных и недельных записей наблюдений за детьми с ОВЗ.
Определяет типы материалов по именам файлов, проверяет комплектность и сохраняет
результаты в PostgreSQL. Реализованы три REST-эндпоинта.

## Быстрый запуск

Нужны работающий Docker Engine и Docker Compose v2. В каталоге проекта:

```sh
docker compose up
```

Compose собирает приложение, запускает PostgreSQL, дожидается готовности БД и применяет
миграции. Java, Maven и предварительное создание `.env` не нужны. При первом запуске
требуется интернет для образов и зависимостей. Дождитесь сообщения `Started DtaApplication`.

Проверка в другом терминале или браузере:

```sh
curl -i http://localhost:8080/api/checks
```

Ожидается HTTP 200; для новой базы — `{"items":[],"page":0,"size":20,"total":0}`.
API доступен только на локальном интерфейсе. Если порт 8080 занят, задайте `APP_PORT`
в необязательном `.env`. Остановка — `docker compose down`; данные сохраняются в volume.
`docker compose down -v` **удаляет базу со всеми проверками**.

## Быстрая проверка API

Подставьте пути к трём своим непустым файлам. `filename` задаёт проверяемое имя:

```sh
curl -i http://localhost:8080/api/checks \
  -F 'record_type=daily' \
  -F 'files=@/path/to/diary.pdf;filename=observation-diary.pdf' \
  -F 'files=@/path/to/report.docx;filename=session-report.docx' \
  -F 'files=@/path/to/feedback.png;filename=parent-feedback.png'
```

Ожидается HTTP 201, `status: complete`, пустой `issues` и UUID в `check_id`.
Для `weekly` добавьте `specialist-conclusion.pdf`. Отправка только одного обязательного
материала вернёт HTTP 201 и `incomplete`: неполный комплект является результатом проверки.

```sh
curl 'http://localhost:8080/api/checks?record_type=daily&status=complete&page=0&size=10'
curl 'http://localhost:8080/api/checks?from=2026-01-01T00:00:00Z&to=2027-01-01T00:00:00Z'
curl http://localhost:8080/api/checks/UUID_ИЗ_ОТВЕТА
```

| Метод | Путь | Результат |
|---|---|---|
| POST | `/api/checks` | Multipart: `record_type` и повторяемое поле `files`; сохранённый результат, HTTP 201 |
| GET | `/api/checks` | `items`, `page`, `size`, `total`; каждый элемент содержит ID, дату, тип, статус, количество документов |
| GET | `/api/checks/{id}` | Полный результат с документами и нарушениями; HTTP 404 для отсутствующего UUID |

Фильтры списка необязательны: `record_type`, `status`, `from`, `to`.
Дата `from` включается, `to` исключается; даты передаются в ISO 8601 с часовым поясом.
`page` начинается с 0, `size` по умолчанию 20, допустимо 1–100.
Сортировка: дата проверки по убыванию, затем UUID по убыванию при одинаковой дате.

Полный результат содержит `check_id`, `status`, `status_label`, `reason`, `issues`,
`documents`, `extracted`, `checked_at`. Нарушение: `level` и `message`.
Документ: `name`, `detected_type` (может быть `null`), `size_kb` (байты / 1024, два знака).
Время возвращается в UTC. Повторный POST создаёт самостоятельную проверку.

## Правила проверки

| Тип материала | Фраза в имени (русская или английская) | Обязателен |
|---|---|---|
| `observation_diary` | дневник наблюдений / observation diary | daily, weekly |
| `session_report` | отчет о занятии / session report | daily, weekly |
| `parent_feedback` | обратная связь родителя / parent feedback | daily, weekly |
| `specialist_conclusion` | заключение специалиста / specialist conclusion | weekly |

Регистр не важен; `ё` приравнивается к `е`; пробелы, дефисы и подчёркивания разделяют слова.
Можно добавлять даты и другие слова вокруг фразы. Сокращения не распознаются.
Несколько разных типов в одном имени дают предупреждение о неоднозначности.

- Разрешены расширения PDF, DOCX, XLSX, JPG, PNG, без учёта регистра.
- Неверный формат, пустой файл, размер больше 20 МиБ, неизвестное или неоднозначное имя — `warning`.
- Файл с неверным форматом, пустой или превышающий 20 МиБ не закрывает обязательный тип.
- Отсутствие обязательного типа — `error`; хотя бы одна такая ошибка означает `incomplete`.
- Без ошибок статус `complete`, в том числе при наличии предупреждений.
- Дубликаты допустимы, но не заменяют другие типы материалов.

POST принимает 1–20 файлов. Имя — до 255 Unicode-символов, без управляющих символов
и разделителей пути. Транспортный предел — 25 МиБ на файл, 120 МиБ на весь multipart-запрос.
Это отдельные пределы: файл между 20 и 25 МиБ принимается для формирования предупреждения.

Ошибки API имеют вид `{"code":"...","message":"...","field_errors":[]}`.
HTTP 400 — повреждённый multipart или неверный формат параметра; 422 — недопустимые
поля/диапазоны; 404 — проверка не найдена; 413 — транспортный лимит; 415 — неподходящий
Content-Type; 503 — недоступная БД; 500 — внутренняя ошибка без раскрытия деталей.
При загрузке существенно больше лимита сервер может закрыть соединение, не дочитав тело.

## Границы реализации

Java-стек выбран по согласованию вместо Python из исходного задания.
Проверяется **имя, расширение и размер**, а не фактическое содержимое документа.
AI/OCR и извлечение данных не подключены: `extracted: null` честно обозначает это ограничение.
Сохраняются результаты и метаданные; содержимое файлов постоянно не хранится.
Авторизация, версионность дневных записей и скачивание файлов вне согласованного объёма.
Проверка синхронная: POST возвращает конечный статус; `check_in_progress` предусмотрен
в модели, но отдельная фоновая обработка не реализована.

## Тесты и сборка

Для тестов нужны JDK 21 и доступ текущего пользователя к Docker. Maven устанавливать
не нужно: Wrapper фиксирует 3.9.16. Проверьте JVM через `./mvnw -version`.

```sh
./mvnw -B -ntp verify
```

Команда проверяет Java 21 (Enforcer), стиль (Checkstyle), запускает все тесты,
собирает JAR и создаёт JaCoCo-отчёт `target/site/jacoco/index.html`.
Отчёты тестов — `target/surefire-reports`. Процентного порога покрытия нет.
На Windows используйте `mvnw.cmd` вместо `./mvnw`.

Testcontainers самостоятельно запускает изолированный PostgreSQL 17.11, применяет Flyway
и удаляет тестовые контейнеры. Предварительный `docker compose up` и `.env` для тестов
не нужны; запущенное приложение останавливать не требуется.
Сборка образа пропускает выполнение тестов, поэтому запуск Compose не заменяет `verify`.

Только доменные тесты, без Docker (это не полная проверка):

```sh
./mvnw '-Dtest=ru.dta.check.domain.*Test' test
```

| Правила / сценарии | Основные тесты |
|---|---|
| Имена, языки, нормализация, неоднозначность | `MaterialTypeDetectorTest` |
| Комплектность, предупреждения, границы размера, дубликаты | `RecordCheckerTest`, `RecordCheckerResultTest` |
| Инварианты и неизменяемость результатов | `MaterialMetadataTest`, `CheckResultTest`, `CheckEntityTest` |
| HTTP-контракт, ошибки, преобразование DTO, время | `CheckControllerTest`, `CheckResponseMapperTest`, `CheckServiceTest` |
| Реальная HTTP-загрузка, лимиты и откат после записи | `CheckApiIntegrationTest` |
| Фильтры, сортировка, страницы, детали, отсутствие N+1 коллекций | `CheckGetIntegrationTest` |
| PostgreSQL, ограничения, миграции, атомарность | `CheckPersistenceTest`, `DtaApplicationTest` |

GitHub Actions выполняет `verify`, запускает Compose без `.env` и проверяет сохранность
результата после перезапуска БД и приложения для push и pull request. Статус последнего запуска
нужно смотреть во вкладке Actions; наличие workflow само по себе не доказывает его успех.
Версии действий CI сверены с официальными инструкциями
[setup-java](https://github.com/actions/setup-java) и [checkout](https://github.com/actions/checkout).

## Технологии и архитектура

| Технология | Назначение и причина выбора |
|---|---|
| Java 21 | LTS, строгая типизация и стандартные средства для моделей данных |
| Spring Boot 4.1.1 | REST, конфигурация и внедрение зависимостей |
| PostgreSQL 17.11 / Hibernate / Flyway | Транзакционное хранение, JPA и версионируемая схема |
| Lombok / MapStruct | Меньше шаблонного кода, преобразование DTO с проверкой при компиляции |
| JUnit / Mockito / Testcontainers | Бизнес-тесты, изоляция границ, интеграция с настоящей БД |
| Maven Wrapper / Enforcer / Checkstyle / JaCoCo | Единая сборка, версия Java, стиль и поиск пробелов в тестах |
| Docker Compose | Единый запуск приложения и БД без установки Java |

Один Maven-модуль, пакеты имеют отдельные обязанности:

```text
check.api          REST, входные параметры, DTO, MapStruct, HTTP-ошибки
    ↓
check.application  сценарии, транзакции, запросы и сводные результаты
    ↓
check.domain       правила проверки, без Spring и JPA
check.persistence  JPA-сущности и репозиторий
config             создание общих компонентов, включая Clock
```

POST сохраняет проверку, документы и нарушения одной транзакцией в трёх таблицах.
Flyway управляет схемой; Hibernate только проверяет соответствие (`validate`).
Для GET детали коллекции загружаются внутри транзакции сервиса; `open-in-view` выключен.
Список считает документы групповым запросом, не загружая каждый документ каждой проверки.
Внешних интеграций, брокеров, кэша и отдельных Maven-модулей нет.

## Конфигурация

Все переменные `.env.example` необязательны. Для изменения значений можно скопировать
его в `.env`; сам `.env` исключён из Git и Docker build context.

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `POSTGRES_DB` | `dta` | Имя базы |
| `POSTGRES_USER` | `dta` | Пользователь БД |
| `POSTGRES_PASSWORD` | `dta-local-demo` | Пароль для локальной демонстрации |
| `APP_PORT` | `8080` | Порт API на компьютере |

Compose передаёт одинаковые реквизиты БД обоим контейнерам. Демонстрационный пароль
предназначен для локального запуска; для размещения вне своего ПК задайте собственный.
Изменение пароля в `.env` не меняет пароль уже созданной базы в существующем volume.
Порт PostgreSQL наружу не публикуется, приложение работает от непривилегированного пользователя.

Для запуска Java напрямую нужны переменные `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`,
указывающие на доступный PostgreSQL. Spring Boot самостоятельно `.env` не читает:

```sh
./mvnw spring-boot:run
```
